# 인수 기준과 검증 기록

기준일: 2026-10-14. 계약: [CONTRACTS.md](CONTRACTS.md). 설계: [DESIGN.md](../DESIGN.md). 단계: [IMPLEMENTATION_PLAN.md](../IMPLEMENTATION_PLAN.md).

이 문서는 요구사항 ID별 완료 시나리오와 검증 결과를 기록한다. 아래 상태는 모두 **미실행**으로 시작한다. 구현했거나 자동 테스트가 통과했다는 사실만으로 상태를 바꾸지 않고, 이 문서의 시나리오를 실제로 수행한 뒤 기록 양식으로 근거를 남긴다.

## 1. 판정 규칙

- 상태는 `미실행` / `통과` / `실패` / `제외(사유)` 중 하나다. 실행하지 못한 검증은 이유를 적고 `미실행`으로 둔다. 추정으로 `통과`를 적지 않는다.
- 검증 방법: **자동**(저장소의 테스트 명령), **수동**(사람이 브라우저·기기에서 수행), **통합**(실제 Supabase 개발 프로젝트와 테스트 계정 사용).
- mock이나 가짜 scheduler로 얻은 결과는 단위 검증이다. 실제 회원가입·게시판·인증 항목은 **통합** 검증을 마치기 전에 `통과`로 바꾸지 않는다.
- C 컴파일러나 Supabase 프로젝트·테스트 이메일이 없어 못 한 검증은 `미실행`이며, 이유를 기록한다.
- 줄 매핑의 의미(이 줄이 이 연산에 맞는가)는 검증기가 확인하지 못한다. 매핑을 바꿀 때마다 수동 검토를 기록한다.
- 테스트 계정과 게시글만 사용한다. 기록에 이메일·키·토큰 값을 적지 않는다(계정은 A, B로만 표기).

### AC-01 (일부) — 03단계 검토 지적 2건 수정 (구현자 확인, 독립 재검토 전)

- 날짜: 2026-10-14
- 검증자: Claude(구현자). 지적은 독립 검토(Codex)가 재현했고, 구현자가 같은 사례를 직접 재현한 뒤 수정했다.
- 지적 1: **시작 노드를 발견하지 않은 BFS가 검증을 통과**했다. `initial → finish`로 줄이고 상태를 모두 비우면 `{valid:true}`였다. 원인은 전이 규칙이 모두 "어떤 operation이 나타났을 때" 적용되어, operation이 하나도 나타나지 않는 trace가 어느 규칙에도 걸리지 않은 것이다. 03단계 기록의 "최종 결과 비교는 필연적으로 참이라 죽은 코드"라는 판단이 틀렸다.
  - 수정: (a) step 1은 반드시 `discover`(시작 노드)여야 한다는 규칙 추가, (b) 제거했던 입력 기반 독립 BFS 계산(최종 `discovered`·`processed` 비교)을 다시 넣어 마지막 방어선으로 둔다.
  - 회귀 테스트: 재현 사례(`initial → finish`)와 변형(첫 연산이 `dequeue`·`check-neighbor`·`process`·`enqueue`, 시작만 발견하고 종료, 탐색 없이 처리 완료, A만 처리하고 종료, 한 노드 그래프의 빈 trace)을 추가했다. 정상 trace(한 노드 그래프의 6 step)는 계속 통과한다.
  - 두 방어선이 실제로 각각 작동하는지 변이 검사로 확인했다. (a)만 제거하면 그 규칙 이름을 직접 단언한 테스트 1개가 실패하고 나머지는 (b)가 막아 통과하며, (b)만 제거하면 시작은 발견했지만 결과가 틀린 사례 2개가 실패하고, (a)와 (b)를 모두 제거하면(수정 전 상태) 7개가 실패해 재현 사례가 통과하지 못한다.
  - **건전성 테스트 추가(`tests/frontend/trace-soundness.test.mjs`)**: 같은 유형의 구멍이 더 있는지 사례를 떠올리는 대신 체계적으로 확인했다. BFS의 (operation, 상태) 열은 입력이 정해지면 하나뿐이므로 "통과한 trace는 항상 정답과 같다"가 성립해야 한다. 시드가 고정된 무작위 그래프 150개(1~6노드, 자기 간선·사이클·합류 포함)에서 정답을 만들고, 모든 위치에 7종 훼손(step 삭제, 복제, 인접 교환, 조기 종료, operation 바꾸기, 상태 값 바꾸기, 입력만 교체)을 가해 **10,560개 사례 중 정답과 다른데 통과한 trace가 0개**임을 확인한다(약 2초). 정답 trace는 150개 모두 통과한다. 수정 전 상태를 재현하면 이 테스트 2개가 모두 실패한다. 이 과정에서 검증기의 추가 결함은 발견되지 않았다.
- 지적 2: **`loadBundle(..., {catalog})`로 넘긴 catalog는 검증을 건너뛰었다.** 경로를 `bfs/../bfs/diamond.json`으로 바꾼 catalog를 `validateCatalog`는 거부하지만 `loadBundle`은 파일을 요청해 성공했다. 기존 `startsWith(baseUrl.href)` 안전장치는 URL 정규화 뒤 폴더 안으로 보이므로 이 경로를 막지 못했다.
  - 수정: 넘긴 catalog를 먼저 `structuredClone`으로 복사하고, **복사본**을 검증한 뒤 얼려서 쓴다. 검증 뒤 `await` 사이에 호출자가 원본 객체를 바꿔도(예: `languages`) 검증하지 않은 값을 쓰지 않는다. 복사할 수 없는 값(함수 등)과 `null`도 `invalid-catalog`로 거부하며, 생략(`undefined`)만 "없음"으로 보고 직접 읽는다.
  - 회귀 테스트: 재현 사례와 폴더 밖·외부 주소·다른 예제 경로·잘못된 알고리즘·`{}`·`[]`·문자열·숫자·`null`·함수가 든 catalog(모두 `invalid-catalog`, 파일 요청 0건), 요청 도중 원본 변경에도 영향 없음, 올바른 catalog는 통과, `undefined`와 `null`의 구분. 로더 규칙을 하나씩 끄는 변이 5개(검증 제거, 검증 호출만 제거, 복사 제거, `undefined`/`null` 혼동, 복사 실패 처리 제거)를 모두 테스트가 감지한다.
- 자동 검증: 건전성 테스트 추가 후 최종 수치는 아래 "최종 실행" 줄을 따른다. (수정 직후 `npm test` 125개, `pytest` 51개, `npm run validate:traces` 1개 통과.)
- 교훈과 적용: 변이 검사에서 못 잡은 항목을 "중복"이라고 결론 내리기 전에 그 규칙만 어기는 반례 trace를 직접 만들어 본다. 이번에는 이 단계를 건너뛰어 틀린 결론을 기록에 남겼다. 같은 이유로 DFS·이분 탐색·버블 정렬의 규칙(06단계)을 만들 때도 "아무 operation도 하지 않은 최소 trace"(initial → 종료)를 반례 사례에 포함한다.
- 최종 실행(2026-10-14): `npm test` 127개 통과(건전성 테스트 2개 포함, 약 2초), `pytest` 51개 통과, `npm run validate:traces` 1개 통과. 규칙 제거 변이 검사는 기존 38개와 로더 5개를 포함해 모두 테스트가 감지했다(이중 방어선 두 항목은 위에 설명한 대로 한쪽만 제거하면 해당 규칙을 직접 단언한 테스트가 실패한다). 8000 포트와 테스트용 node 프로세스는 남기지 않았다.

### 06단계 — 독립 검토 [P2] 수정 (다시 시도 뒤 포커스 유실, 구현자 확인, 독립 재검토 전)

- 날짜: 2026-10-15
- 검증자: Claude(구현자). 지적은 독립 검토(Codex)가 Chrome에서 재현했다(404 → "다시 시도"에 Enter → 예제는 열리지만 포커스가 BODY로 이동).
- 원인: `visualizer.js`의 `show()`가 예제를 불러오기 시작할 때 재시도 버튼(과 오류 상세, 본문, 조작 버튼)을 **포커스를 옮기지 않고** 숨기거나 막았다. 숨겨진 요소에서 포커스가 사라지는 것은 브라우저의 규칙인데, **가짜 DOM이 이 규칙을 흉내 내지 못해서** 자동 테스트가 못 잡았다(04단계의 비활성 버튼과 같은 종류의 허점이다. 그때는 비활성만 모델링했고 숨김은 하지 않았다).
- 수정:
  - `focus-guard.js`(`moveFocusOutOf`, `firstUsable`): 숨기거나 막을 요소 안에 포커스가 있으면 **숨기기 전에** 쓸 수 있는 요소로 옮긴다(비활성 요소에는 `focus()`가 실패하므로 옮길 곳은 활성인 요소만 고른다).
  - `show()`: 재시도 버튼·오류 상세·본문·조작 버튼 중 하나가 포커스를 가졌으면 예제 선택 상자(없으면 알고리즘 선택 상자, 둘 다 못 쓰면 `tabindex="-1"`인 상태 영역)로 먼저 옮긴다. **다시 실패하면** 사용자가 포커스를 옮기지 않았을 때만 재시도 버튼으로 돌려놓는다(Enter를 다시 누를 수 있게). 사용자가 옮겼다면 빼앗지 않고, 선택 상자로 고른 예제가 실패한 경우에도 가져가지 않는다.
  - `open()`: 포커스가 상태 영역에 있었다면(선택 상자를 쓸 수 없는 목록) 숨기기 전에 조작 버튼으로 옮긴다.
- 가짜 DOM 보강(`fake-dom.mjs`, `fake-page.mjs`): 부모·자손 연결과 `contains`, **숨긴 요소(와 그 자손)에는 `focus()`가 실패하고 포커스를 가진 채 숨기면 포커스가 body로 간다**(즉시 정리하는 브라우저와 다음 렌더링 때 정리하는 브라우저 두 방식), 시각화 페이지에서는 button·select·summary·`tabindex`가 있는 요소만 포커스를 받는다(엄격 모드). 페이지의 HTML 태그 순서에서 요소 관계를 만든다. 이 보강 뒤 기존 테스트 372개가 그대로 통과했고, 새 회귀 테스트는 수정 전 코드에서 **13개가 실패**하는 것을 확인한 뒤 수정했다.
- 회귀 테스트(두 브라우저 방식 모두): 복구(재시도 → 성공)·**재실패(3번 연속, 매번 포커스가 재시도 버튼에 있음, 이후 복구)**·**로딩 중 사용자가 포커스를 옮김(성공·실패 모두 그 자리 유지)**·오류 상세 요약에 포커스가 있을 때 다른 예제 선택·본문(언어 선택 상자)이나 조작 버튼에 포커스가 있을 때 선택·선택 상자로 고른 예제의 실패(재시도 버튼으로 가져가지 않음)·선택 상자를 모두 쓸 수 없는 목록의 복구, 그리고 `focus-guard.js` 단위 테스트와 가짜 DOM 규칙 자체의 테스트.
- 회귀 테스트가 실제로 결함을 잡는지(변이 검사): 수정 코드를 일부러 망가뜨린 변이 **19개를 모두 감지**했다(옮기지 않음, 영역에서 재시도 버튼·오류 상세·본문·조작 버튼을 뺌, 옮길 곳 선택 오류, 포커스 여부를 옮긴 뒤에 계산, 다시 실패해도 돌려놓지 않음, 사용자가 옮긴 포커스까지 빼앗음, 선택 상자로 고른 예제의 실패에도 가져감, `open()`의 이동 누락, 후손의 포커스를 알아보지 못함, 비활성·숨긴 후보를 고름, `tabindex` 제거). 처음에는 3개가 살아남았다(본문·조작 버튼에 포커스가 있는 경우, 재시도하지 않았는데 재시도 버튼으로 가져가는 경우, 상태 영역의 `tabindex`) → 각각 테스트를 추가하고 가짜 DOM에 "포커스를 받을 수 있는 요소" 규칙을 넣어 해소했다.
- 실제 Chrome 확인(실제 키 입력, 포커스 이동 기록 포함): 404 상태에서 예제 선택 상자로 Tab → "다시 시도"에 포커스, 서버를 복구한 뒤 **Enter → 포커스가 예제 선택 상자로 옮겨지고(`out:viz-retry`, `in:example-select`, BODY를 거치지 않음) 예제가 열렸다.** 서버를 다시 실패시키고 Enter를 두 번 눌러도 매번 포커스가 재시도 버튼으로 돌아왔고, 복구 뒤 Enter에서는 다시 예제 선택 상자에 있었다.
- 자동 검증: `npm test` 396개 통과(건너뜀 0), `pytest` 67개 통과(기존 경고 1개), `npm run validate:traces` 16개 통과, `git diff --check` 통과.
- 판정: 지적 해소. 06단계 완료 조건의 재확인은 독립 검토에 맡긴다. 실제 스크린 리더·Safari·실기기는 계속 미실행이다.

  - **실제 역할 전환**: 비회원 / 회원 A / 회원 B / 프로필 없는 회원 / 관리자(service_role)를 `SET ROLE`로 전환해 실행하고, 전환이 되었는지 매번 확인한다. 같은 문장이 관리자 접속에서는 성공하는 대조 검사도 있다.
  - **거부 항목**: 타인 `author_id`로 삽입, `author_id`·`id`·`created_at`·`updated_at`·`version`·표시명 지정·변경(컬럼 권한), 권한이 넓은 service_role의 불변 컬럼 변경(트리거), 길이·공백·허용 ID 위반(**제약 이름까지** 확인), 닉네임 규칙 20가지, **공백 29개 × 위치(앞·뒤·가운데·본문)** 표 시험, 프로필 삭제.
  - **insert-if-absent**: `ON CONFLICT DO NOTHING`이 0행이고 닉네임이 덮어써지지 않음. 닉네임을 바꿔도 기존 글의 표시명은 그대로, 새 글에는 새 닉네임. 계정 삭제 시 프로필·글 연쇄 삭제.
  - **RPC**: 성공(제목만·본문만·알고리즘만·세 필드·값이 같아도 version 증가), 충돌(오래된·미래 version, 같은 version 두 번째), 남의 글(version이 틀려도 forbidden), 없는 글·삭제된 글(not_found), 입력 오류가 글을 바꾸지 않음, anon 거부, 실패 결과가 글 내용을 돌려주지 않음.
  - **SECURITY INVOKER 증명**: 트랜잭션 안에서 컬럼 권한이나 정책을 빼면 RPC도 실패한다(함수가 소유자 권한으로 실행되었다면 통과했을 것).
  - **방어층 분리**: 컬럼 권한·트리거를 잠시 풀어도 RLS의 WITH CHECK와 CHECK 제약이 따로 막는다. 정책을 "모두 허용"으로 바꿔도 RPC의 명시 조건이 남의 글을 막는다.
  - **동시성(실제 별도 접속)**: 잠금을 쥔 수정 하나와 같은 version으로 기다리는 수정 3개 → 하나만 `ok`, 나머지 `version_conflict`(700ms 이상 실제로 대기). 같은 version으로 8개 접속이 동시에 수정을 6번 반복 → 매번 정확히 하나만 `ok`이고 version은 한 번만 올랐다. 수정 vs 삭제가 겹치면 `not_found`/`version_conflict`. 10개 접속이 같은 글을 동시에 삭제 → 하나만 `ok`.
- 변이 검사(임시 복사본에서 migration을 일부러 망가뜨림): **85개를 모두 감지**했다(테이블·제약·인덱스 24, 권한·RLS·트리거 39, RPC 22). 고친 migration·테스트로 85개를 처음부터 다시 적용한 최종 결과이며 생존·적용 실패 모두 0이다.
  - 처음 85개 중 75개를 감지하고 10개가 문제를 드러냈다. 하나씩 분석했다.
    1. 공백 정의에서 U+3000(닉네임 앞)·U+00A0(제목 앞)을 뺀 변이: **앞 위치는 시험하지 않은 테스트 공백**이었다 → 공백 29개 × 위치 표 시험 추가.
    2. 본문 최소 길이 1→0: 빈 문자열을 "공백만 불가" 제약이 대신 거부해 SQLSTATE만으로는 구분되지 않았다 → 테스트가 `SQLSTATE:제약이름`까지 확인하도록 개선.
    3. 알고리즘 값만 주고 플래그가 없는 호출을 허용하는 변이: "바꿀 필드 없음" 검사가 같은 SQLSTATE(22023)로 가렸다 → 제목과 알고리즘을 함께 주는 케이스와 오류 이름 확인 추가.
    4. profiles·posts 수정 정책의 WITH CHECK, posts 작성 정책의 WITH CHECK, update_post·delete_post의 소유자 조건을 없앤 변이: 컬럼 권한·트리거·RLS가 겹쳐 있어 하나가 빠져도 가려졌다 → **방어층 분리 테스트**(바깥 방어를 SAVEPOINT 안에서만 풀고 안쪽만 시험). 이 과정에서 PostgreSQL이 `WHERE`가 컬럼을 참조하는 UPDATE의 새 행도 SELECT 정책으로 검사해 WITH CHECK가 가려진다는 점을 발견해(profiles) `WHERE` 없는 UPDATE로 시험하도록 고쳤다.
    5. "posts 작성 트리거: created_at을 정하지 않음" 변이는 변이 정의의 문자열 오류로 적용되지 않아 정의를 고쳐 다시 적용했다.
  - 동치로 판단한 변이는 없다. 겹친 방어선은 위처럼 따로 시험한다.
- 작업 중 실수와 수정: ① 도구가 U+0020·U+00A0·U+3000 같은 공백 계열 문자의 유니코드 이스케이프(백슬래시 u와 16진수 4자리)를 **실제 문자(보이지 않는 문자, U+2028·U+2029는 줄바꿈 문자)로 바꿔 저장**했다. 정규식으로서는 같은 집합이라 테스트가 통과해 한동안 드러나지 않았고, 변이 검사의 문자열 대조가 맞지 않아 발견했다. 이스케이프로 되돌리고, `tests/db/db-static.test.mjs`가 DB 관련 소스에 그런 문자가 없는지 계속 지킨다. ② 테스트 입력·기대값의 실수: 한 글자 닉네임('씨')을 2자로 잘못 센 입력과, `update_post`가 항상 세 컬럼을 SET하므로 body만 고쳐도 title 권한이 필요하다는 점을 놓친 단언은 실행에서 발견해 고쳤고, 개수를 잘못 센 기대값 2곳은 실행 전에 바로잡았다. 정적 테스트의 `delete from` 금지 규칙이 `delete_post` 자신을 막던 것도 고쳤다. ③ `pg_ctl start`를 파이프로 받으면 돌아오지 않는 문제를 알게 되어 실행기는 `postgres`를 자식 프로세스로 직접 띄운다.
- 판정(표의 상태 칸은 검토자가 갱신): 
  - **DATA-01**: 빈 로컬 PostgreSQL에서 migration을 순서대로 적용해 같은 스키마·RLS·RPC가 만들어짐을 확인했다. **실제 Supabase 프로젝트에 적용한 것은 확인하지 못했다**(미실행). 기존 데이터를 지우는 구문이 없음은 정적 테스트가 확인한다.
  - **AC-07**: DB 역할 수준(Data API가 하는 일과 같은 `SET ROLE`+JWT claim)에서 A가 B의 글을 수정·삭제할 수 없음을 확인했다. FastAPI와 실제 Supabase Data API(PostgREST)를 거친 호출은 11·13단계에서 확인해야 한다.
  - **BOARD-03**: DB의 RPC 결과(404/403/412에 대응)와 동시 수정 충돌은 확인했다. HTTP 상태 변환·If-Match·ETag는 11단계다.
- 남은 이슈·제한:
  - **실제 Supabase 프로젝트에 적용·확인하지 않았다.** 완료 조건 "기존 DB가 있다면 diff를 확인"은 대상 프로젝트에 접속할 수 없어 수행하지 못했고, `supabase/README.md`에 적용 전 점검 절차만 적었다. 대상 프로젝트를 확인하고 적용하는 일이 남았다.
  - Supabase의 PostgREST·Auth(GoTrue)·JWT 서명 검증 경로, Supabase가 쓰는 PostgreSQL 버전(15·17 등)과의 차이는 확인하지 못했다. PostgreSQL 18.3(Windows) 한 가지, `C` 로케일에서만 실행했다. 격리 수준은 `READ COMMITTED`만 확인했다.
  - `supabase db push`(CLI)로 적용하는 방법과 12자리 버전 파일명 호환은 CLI가 없어 확인하지 못했다(계획서의 파일명을 그대로 썼다).
  - 직접 Data API 호출의 공개 운영 시 rate limit은 이 단계의 범위가 아니다(DESIGN.md §7).
  - 계획서 체크박스(08단계 완료 조건 3개)는 구현자가 체크하지 않았다.
- 정리: 임시 클러스터·폴더·프로세스는 모두 종료·삭제했다(남은 `dbtest-*` 폴더와 임시 postgres 프로세스 없음). 사용자의 PostgreSQL 서비스는 실행 상태 그대로다. `.env` 열람·변경, 커밋 없음.

### 08단계 — 독립 검토 [P2] 2건 수정 (migration 사이의 열린 틈, 실행기의 잘못된 통과; 구현자 확인, 독립 재검토 전)

- 날짜: 2026-10-15
- 검증자: Claude(구현자). 지적은 독립 검토(Codex)가 재현했고, 구현자가 같은 사례를 먼저 재현한 뒤 수정했다. 독립 재검토는 아직 하지 않았다.
- **[P2] 첫 migration 직후 권한이 열려 있음** — 원인: 테이블은 `…0001`에서 만들고 RLS 활성화·기본 권한 회수는 `…0002`에 있었다. migration 파일은 하나씩 따로 적용될 수 있는데(SQL Editor, 파일마다 별도 트랜잭션인 CLI, 실행기도 파일마다 별도 트랜잭션) 지난 기록의 "파일은 각각 하나의 트랜잭션"은 파일 **안**의 원자성만 말했고 파일 **사이**의 상태는 검증하지 못했다. Supabase의 기본 권한 아래에서는 `…0001`만 적용된 동안 `anon`이 읽고 쓸 수 있고, 그동안 들어간 행(예: `version=999`)은 `…0002`를 적용해도 정정되지 않는다.
  - 수정: `…0001`이 테이블을 만든 같은 파일에서 두 테이블의 RLS를 켜고 `REVOKE ALL … FROM PUBLIC, anon, authenticated`를 한다(`…0002`에서 같은 문장을 옮겼다). 그래서 `…0001`만 적용된 상태에서는 `service_role`(RLS 우회 역할)만 접근한다. `…0002`는 필요한 권한·정책·트리거만 연다. 함수를 만드는 파일(`…0002`, `…0003`)은 이전부터 같은 파일에서 실행 권한을 회수한다.
  - 테스트(수정 **전** migration에서 실패하는 것을 먼저 확인): 실행기에 `migration_steps`를 추가했다. 빈 DB에 shim과 migration 1만 적용해 `after_migration_1.sql`을, 이어서 migration 2를 적용해 `after_migration_2.sql`을 실행한다(둘을 합쳐 79개 검사). 1만 적용된 상태에서 RLS 켜짐, anon·authenticated의 표·컬럼 권한 없음(7개 권한 종류), PUBLIC 권한 없음, 그리고 리뷰어가 재현한 동작(anon의 프로필·`version=999` 글 삽입, 읽기·수정·삭제, 로그인한 회원의 같은 시도)이 모두 `42501`로 거부되고 `service_role`만 접근됨을 확인한다. 수정 전 migration에서는 첫 검사(`migration 1: profiles RLS 켜짐`)부터 실패했다. 정적 테스트(`tests/db`)는 "테이블을 만드는 파일은 같은 파일 안에서 RLS를 켜고 기본 권한을 회수하며, 함수를 만드는 파일은 같은 파일 안에서 실행 권한을 회수한다"를 검사한다.
- **[P2] 잘못된 테스트 이름이 성공으로 처리됨** — 원인: `--only` 값을 검증하지 않아 이름이 틀리면 아무 스위트도 실행하지 않고 "전체 통과 ()"와 종료 코드 0이 나왔다. 수정: 허용 이름(`migration_steps`, `rls`, `post_mutations`, `concurrency`)을 검증하고(쉼표로 여러 개 가능), 값이 없는 `--only`·`--migrations`·`--tests`, 모르는 인자는 PostgreSQL을 찾기 전에 한국어 메시지와 종료 코드 1로 실패한다. 스위트가 검사를 하나도 실행하지 않으면(파일 단위, 스위트 단위, 전체 합계) 통과가 아니라 실패다. 테스트 폴더를 지정하는 `--tests` 옵션을 추가해 "검사가 없는 테스트는 실패"를 실제로 시험한다(`tests/db`). 이름을 고르면 그 이름만 실행하는 것도 시험한다.
- 자동 검증: `npm test` 464개 통과(건너뜀 0, 이전 461개), `npm run test:db` **683개 통과**(migration_steps 79, rls 508, post_mutations 87, concurrency 9), `pytest` 68개, `validate:traces` 16개, `git diff --check` 통과. 줄바꿈 규칙과 보이지 않는 공백 문자 검사도 통과했다.
- 변이 검사(임시 복사본에서 일부러 망가뜨림): **96개 모두 감지**(migration 변이 88 + 실행기 변이 8). 새로 넣은 것: 잠금에서 `authenticated`만 또는 `anon`만 회수를 빠뜨림(`migration_steps`·`rls`가 감지), **수정 전 구조(잠금을 첫 파일에서 둘째 파일로 미룸)는 `migration_steps`만 감지**한다(최종 상태만 보는 기존 테스트로는 잡지 못한다는 뜻이며 이번 지적을 새 테스트가 정확히 잡는다는 근거다). 실행기 변이: 이름 검증 제거, 값 없는 `--only` 검증 제거(오류 메시지까지 확인하도록 정적 테스트를 고쳐 잡음), `--only` 무시, `--tests` 무시, 실패해도 종료 코드 0, 검사 0개 보호 세 겹을 모두 제거, 단계별 검사에서 migration 2를 적용하지 않음, 단계별 검사가 migration을 한꺼번에 적용함. 검사 0개 보호는 세 겹으로 겹쳐 있어 하나만 빼면 다른 겹이 같은 결과를 내므로 세 겹을 함께 뺀 변이로 시험했다.

  - 설정은 처음 쓸 때 읽는다(서버를 다시 시작해야 `.env` 변경이 반영됨). 환경 변수가 `.env`보다 우선하고 `.env`를 읽어도 `os.environ`을 바꾸지 않는다.
